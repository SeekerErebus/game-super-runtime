# User assignment — 2026-10-15 (verbatim)

This folder contains v01 of game-super-runtime. I am thoroughly impressed with what has already been built, however I want to make a significant improvement. Specifically, virtual directory support.
The idea here is that when the proton runtime especially—and other wrappers potentially—see the directory structure in which they are working, other aspects of the file system will have already been symlinked in seamlessly.
One example use-case would be a companion app, installed into a prefix at ~/Games/Prefixes/WeMod, having the executable directory and it's associated windows app-data seen by proton as inside of the identical file structure for the game's prefix. This enables installing a windows application used by multiple games once, and having it supported everywhere. I use Wemod as an example because Wemod Launcher is a linux project trying to do exactly this with that program.
Another use case would be the Mod Organizer 2/Vortex use case. One directory contains a list of mod directories, which contain the files which mods will use. Another contains the instructions of which are active and in what order. At runtime, all of the mod files which are active are virtually merged into a single overwrite which proton and the game itself sees as native files. Full piping integration with MO2/Vortex is not required, but it would be useful if it could be plugged in later by a compatibility tool without requiring an update of game-super-runtime.
I had originally instructed that this project use minimal dependencies. I am adjusting that instruction: this functionality can use the dependencies already best suited for it, however when a yaml file does not need this functionality, the dependencies can be optional, with a proper error provided should it be attempted and lack the dependencies. I may be incorrect, but I think FUSE is purpose built for this, and I do not know how solid the Ubuntu stack is at supporting FUSE.
Additionally, `./testing-notes/` contains the testing of functionality already built. I am impressed, but I might not see an improvement discovered in there. If you do, and it remains aligned with the project goals, implement it. Make it happen.
